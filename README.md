# mocks-to-playwright

An adapter that serves mocks generated by the [har-to-mocks](https://github.com/peterknezek/har-to-mocks) in [Playwright](https://playwright.dev) tests through `page.route()`.

[![Version](https://img.shields.io/npm/v/mocks-to-playwright.svg)](https://npmjs.org/package/mocks-to-playwright)
[![Downloads/week](https://img.shields.io/npm/dw/mocks-to-playwright.svg)](https://npmjs.org/package/mocks-to-playwright)
[![License](https://img.shields.io/npm/l/mocks-to-playwright.svg)](https://github.com/peterknezek/mocks-to-playwright/blob/main/package.json)

> Using **MSW** instead? [mocks-to-msw](https://github.com/peterknezek/mocks-to-msw) serves the same mocks as MSW handlers.

## Motivation

Playwright can replay a whole recording with `page.routeFromHAR()`. A HAR file is one large blob, though: hard to read, hard to edit, and changing a single response for one test means editing the recording or layering routes over it by hand.

[har-to-mocks](https://github.com/peterknezek/har-to-mocks) splits a recording into one JSON file per endpoint and method. _"mocks-to-playwright"_ serves those files in Playwright tests with typed calls, so you can:

- read and edit every response as a plain JSON file,
- choose exactly which endpoints each test mocks,
- change a response for a single test with a modifier,
- get a type error when a path has no mock for the method you use.

## Features

- Type-safe mocks that ensure URLs are used with their correct HTTP methods
- Works with a `Page` or a whole `BrowserContext`
- Response modifiers to transform mock data
- Matching by pathname and method, optionally by origin; the query string is ignored
- Cross-origin APIs work out of the box (see [CORS](#cors))
- Debug mode for development
- Automatic mock file generation with type safety

## Installation

```sh
npm install mocks-to-playwright --save-dev
```

`@playwright/test` (1.29 or newer) is a peer dependency. Refer to the [Playwright documentation](https://playwright.dev/docs/intro) to set it up.

## How It Works

1. Generate Mocks: Use _"har-to-mocks"_ to generate mocks from actual server responses.
2. Generate Mock Imports: Use the built-in generator to create type-safe mock imports.
3. Set Up Mock Routes: Use the `createMockRoutes` function provided by _"mocks-to-playwright"_ and register the mocks in your tests.

### Automatic Mock Generation

The package includes a CLI tool that generates type-safe mock imports from your JSON mock files.

#### Setup

Add this to your package.json scripts:

```json
{
  "scripts": {
    "generate-mocks": "generate-mocks --folder='tests/mocks/api' --output='tests/mocks/mocks.ts'"
  }
}
```

#### Project Structure

```
project/
  ├── tests/
  │   └── mocks/
  │       ├── api/                    # Input folder for JSON mocks
  │       │   └── client/
  │       │       ├── GET.json
  │       │       └── application/
  │       │           ├── GET.json
  │       │           └── POST.json
  │       └── mocks.ts               # Generated output file
```

#### Generated Output

Running the generator creates a `mocks.ts` file with all your mock imports:

```ts
// tests/mocks/mocks.ts
const mocks = {
  '/client/application/GET': import('./api/client/application/GET.json', { with: { type: 'json' } }),
  '/client/application/POST': import('./api/client/application/POST.json', { with: { type: 'json' } }),
  '/client/GET': import('./api/client/GET.json', { with: { type: 'json' } }),
} as const;

export default mocks;
```

The `{ with: { type: 'json' } }` import attribute is required: Playwright runs your tests in Node.js, which refuses to import JSON without it. Bundlers such as Vite accept it as well. For TypeScript, set `"module"` to `"esnext"`, `"nodenext"` or `"preserve"` in the tsconfig that covers your tests.

#### Using it together with mocks-to-msw

The generator has the same CLI and the same file layout as the one in [mocks-to-msw](https://github.com/peterknezek/mocks-to-msw), so one `mocks.ts` can feed both your MSW handlers and your Playwright tests. Both packages install a `generate-mocks` command. The mocks-to-msw generator does not write the import attribute yet, so when both packages are installed, call this one explicitly:

```json
{
  "scripts": {
    "generate-mocks": "node node_modules/mocks-to-playwright/dist/generate-mocks.js --folder='tests/mocks/api' --output='tests/mocks/mocks.ts'"
  }
}
```

## Usage

### With a page

```ts
import { test, expect } from "@playwright/test";
import { createMockRoutes } from "mocks-to-playwright";
import mocks from "./mocks/mocks";

const { mock } = createMockRoutes<keyof typeof mocks>({
  mocks,
  origin: "https://api.example.com", // optional
  debug: true, // optional
});

// Define response types for better type safety
interface Client {
  id: string;
  name: string;
  email: string;
}

test("shows the client", async ({ page }) => {
  // GET request with type-safe response
  await mock.get<Client>("/client")(page);

  // POST request with response modifier
  await mock.post("/client/application", (data) => ({ ...data, status: "approved" }))(page);

  await page.goto("/");
  await expect(page.getByText("John Doe")).toBeVisible();
});
```

`mock.get()`, `mock.post()`, `mock.put()` and `mock.delete()` return a function. Call it with a page (or a browser context) to register the mock, and `await` it before the app sends the request.

### With a browser context

A mock registered on the context applies to every page in it, including popups and pages opened later:

```ts
test("shows the client in a new tab", async ({ context, page }) => {
  await mock.get("/client")(context);
  // ...
});
```

Page routes take precedence over context routes, so a mock registered on the page overrides the same mock on the context.

### Several mocks at once

Keep the mocks most tests need in one array, the same way you keep MSW handlers, and register them with `applyMocks`:

```ts
import { applyMocks } from "mocks-to-playwright";

export const defaultMocks = [mock.get("/client"), mock.get("/client/application")];

test.beforeEach(async ({ page }) => {
  await applyMocks(page, defaultMocks);
});
```

`applyMocks` registers the mocks one after another, in the order of the array.

To have the default mocks on every page without a `beforeEach`, extend the `page` fixture:

```ts
// tests/fixtures.ts
import { test as base } from "@playwright/test";
import { applyMocks } from "mocks-to-playwright";

export const test = base.extend({
  page: async ({ page }, use) => {
    await applyMocks(page, defaultMocks);
    await use(page);
  },
});
```

### Overriding a mock in one test

Register the same mock again with a modifier. The route registered last wins:

```ts
test("shows an approved application", async ({ page }) => {
  // defaultMocks are already applied by the fixture or the beforeEach
  await mock.get("/client/application", (data) => ({ ...data, status: "approved" }))(page);

  await page.goto("/");
  await expect(page.getByText("approved")).toBeVisible();
});
```

### Route order and matching

- **The route registered last is checked first.** That is Playwright's rule for `page.route()`, and it is why a later mock overrides an earlier one. Page routes are checked before context routes.
- **Pathname and method.** A mock matches when the request's pathname equals the mock's path and the method equals the mock's method. With the `origin` option, the origin must match too; without it, requests to any origin match. Paths are compared literally (no `:param` or `*` patterns).
- **The query string is ignored**, the same way MSW ignores it: `mock.get("/client")` also serves `/client?page=2`.
- **Anything else falls back.** For a request with another method, the mock calls `route.fallback()`, so other routes (including the mocks for the other methods of the same path) still get their chance. Navigation requests (`page.goto("/client")`) are never mocked either, so a page whose URL equals an API path still loads your app instead of JSON (the MSW 2 service worker skips them for the same reason).
- **A mock that fails to load falls back too**, and with `debug: true` it logs the error.

### CORS

Apps often call an API on another origin, and a fulfilled response still goes through the browser's CORS checks. You do not need to configure anything for that: Playwright handles it whenever routes are active.

- It answers CORS preflight (`OPTIONS`) requests itself, allowing the requested method and headers. The mocks never see them.
- It adds `access-control-allow-origin` (set to the requesting origin) and `access-control-allow-credentials: true` to every fulfilled cross-origin response.

The integration tests of this package cover a cross-origin GET, a cross-origin POST with a JSON body (which needs a preflight), and a request with `credentials: "include"` and an `Authorization` header. They run in Chromium.

### Options

| Option   | Type      | Description                                                                                           |
| -------- | --------- | ----------------------------------------------------------------------------------------------------- |
| `mocks`  | `object`  | The generated mocks: `{ "/path/METHOD": import("./path/METHOD.json", { with: { type: "json" } }) }`. |
| `origin` | `string`  | Optional. Scheme, domain and port of the API, e.g. `"https://api.example.com"`.                       |
| `debug`  | `boolean` | Optional. Logs every loaded mock and every mock that failed to load.                                  |

With `debug: true` the logs look like this:

```
[mocks-to-playwright] Mock file was loaded. [GET]: "/client"
[mocks-to-playwright] Mock file was not found. [GET]: "/client/application" Error: ...
```

### Type safety

The paths accepted by each method come from the keys of `mocks`:

```ts
await mock.get("/client")(page); // OK: there is a GET mock for "/client"
await mock.post("/client/application")(page); // OK: there is a POST mock

await mock.post("/client")(page); // Type error: "/client" has no POST mock
await mock.get("/unknown")(page); // Type error: no mock at all
```

## Project Description

_"mocks-to-playwright"_ serves as an adapter, facilitating the integration of mocks generated from the _"har-to-mocks"_ CLI into **Playwright** tests. The typical workflow involves using _"har-to-mocks"_ to generate mocks from actual server responses _(network record in the .har)_, and _"mocks-to-playwright"_ serves these mocks through Playwright's request routing.

### Why Use "mocks-to-playwright"?

- **Type Safety**: Ensures URLs are used with their correct HTTP methods
- **Efficient Mock Management**: Clear organization of mocks in dedicated folders
- **Response Modification**: Ability to transform mock data for a single test
- **Debug Support**: Helpful logging during development
- **URL Configuration**: Optional origin configuration for complete URLs
- **Automatic Mock Generation**: CLI tool to generate type-safe mock imports
- **One Set of Mocks**: The same `mocks.ts` works with [mocks-to-msw](https://github.com/peterknezek/mocks-to-msw)
